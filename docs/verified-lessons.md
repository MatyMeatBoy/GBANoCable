# Verified lessons

Each lesson: the **trigger** (what you see), the **mechanism** (why), the **check** that showed it or guards it, and
its **limits**. A lesson is here because a measurement or a reproduced failure stands behind it; where only the
code was read, the lesson says so. Apply the mechanism to your game; do not copy the constants.

How to add one: [CONTRIBUTING.md](../CONTRIBUTING.md).

## Online

| Trigger | Mechanism | Check | Limits |
|---|---|---|---|
| The transport passes every consistency test and people say items come late, enemies arrive one by one, players stand in different places | The game is not lockstep: it replicates state and passes one-time events as stop-and-wait messages inside the blocks. Each step costs a round trip; behind a delay of `d` frames about `2d + 2` frames | Read who writes the send buffer and who reads the receive buffers before designing ([docs/09](09-multi-sio-anatomy.md)). Measured: about 650 ms per message at 60 ms of simulated latency, about 100 after carrying messages whole | One game, one machine, simulated latency. Scripted players pressing the same buttons hid it: test with people early |
| Each player's events arrive reliably and in order, yet now and then one machine has an enemy or an item the others lack | Per-sender order is not enough: handlers depend on what another player's message did before. On the cable every step waited for everybody, which made one order | One numbered stream through the host; compare every player's dispatch log (sender, kind, hash) ([docs/10](10-direct-transport-and-messages.md)) | The order was verified by logs; combat with deaths and respawns under it was not reached by scripts |
| A player freezes on the others' screens after a lag spike of a second, while enemies and items go on | Unacknowledged blocks are repeated only 40 back; a longer silence leaves a hole the receiver waits for and that no datagram will bring | A relay that cuts one player off: 0 of 36 sessions whole before, 60 of 60 after the receiver steps over a hole. `reference/tests/test_direct.c` shows both | The outage is the relay not forwarding, on one machine |
| A message handler loses the third of three things that arrive together | The handler has a small fixed pool sized for the cable's pace (two spawn requests at a time); online several messages are acted on in one frame | Found from a real session (an enemy only some players had); fixed with an ordered waiting list | The fix rests on reading the code: no scripted run reaches it |
| Companions stop being shown and never return, although they are still playing | Two causes read from the code: the game restarts its own link task on some changes of place and the layer said goodbye for it; a program that stood still (window dragged) counted its own pause as everybody's silence. A player given up stays a standing character for good | A session log beside the program; delay the goodbye two seconds; restart the silence clocks after a stall | Neither cause was reproduced; the report did not come again in testing |
| After an outage the returning player has every event and is still in the wrong place | The game started the next map behind a barrier by a state shown in the host's block only while the barrier stood. Replay restores messages, not state shown in passing | A test that follows the session through a change of map with a player cut off; the report checks "same map" and "no barrier token left over" ([docs/11](11-departures-and-reconnect.md)) | Decision taken: lock the player out. Resynchronising it at the barrier is not built |
| Skipping a scene online ends in a communication error | The skip ran the game faster than real time; the game counts its waits for the other players in frames and they all ran out | Reported with three players; online the scene is ended through the game's own exit at normal speed. Measured with three scripted players: all in the field after about 9,000 frames instead of about 26,000 | The cause was found by reading how the game waits, not reproduced with three machines |
| A late program enters the room and the session stops making progress | Without join in progress the layer takes any stream on a free seat for a player; the game has no record for it | One comparison run: 12 messages dispatched in the whole run. Keep such a program out, or build [docs/12](12-join-in-progress.md) | One run |
| Two builds of the port do not find each other | Intended: the room is the name hashed with the ROM, a rules number and the transport | Raise the rules number whenever players must agree on something new; when only one side decides (the host), keep the number and say who updates first | |
| A frame-counted lag simulator deadlocks the test | A game that waits makes no frames, so the delayed packet is never released | Simulate lag, jitter and outages in wall-clock time, in the relay ([docs/13](13-relay.md)) | |
| Under rollback a desync that never heals, rare, in a few packet words only | The parent's packet carries a copy of received data; a replay changes it and the revision arrives after the other side made the frame final | `tools/pairdiff.py` on both traces: differences only in the relayed words. Derive the copy on every machine ([docs/04](04-netplay-approaches.md)) | ReKHCoM; 55 of 8091 pairs before, 0 revisions after |
| Two equal PCs never desync; a slow device does | An exchange ran on frames where the pair had not arrived yet; equal machines happened to align | Test builds of different speed or processor against each other | ReKHCoM |

## Porting

| Trigger | Mechanism | Check | Limits |
|---|---|---|---|
| A menu crashes every time it opens, on every build | The function addresses its original stack frame through a pinned stack pointer; with the pin stripped the pointer is null | The build refuses a function with that pin unless a patch gives it a real frame ([docs/15](15-native-port-mechanisms.md) §1) | |
| x86 builds agree, ARM64 differs from some frame on | Declarations that disagree between files (a `u16` here, an `s32` there; a struct by value here, words there). ARM and x86 forgive it; arm64_32 packs small stack arguments and trusts the caller's extension | Per-frame hashes → call trace of the first differing frame → a value print. Generated narrowing fixed 375 definitions at once | The lasting repair is in the decompilation |
| Builds drift apart on the first `% 0` | The cartridge's division routines return quotient 0 and remainder 0 by zero; x86 traps, ARM64 returns the dividend as remainder, WebAssembly traps for good | Read the ROM's own routines; give every build those results (fault handler, or a rewrite of the IR before optimisation) | Unifying on one processor's native result is wrong unless it is the cartridge's |
| The game refuses to save at all | The port presented the flash chip's identifier in the wrong place | Call the game's own save routine at a scripted frame and read its answer before anybody plays | |
| A run is judged on old logs | A long scripted input passed in an environment variable was silently dropped (above about 32 KiB) by the wrapper script; the game ran with no input and the old logs stayed | Long data in a file; make the run print what it loaded; delete logs before a run | |
| The fifth setting erases the scripted input | A minimal C library in the game image recycled four `getenv` buffers | Give test settings a `getenv` whose results stay valid | |
| The picture is "the same" after an optimisation, by eye | A state hash does not change when drawing breaks | One hash over every picture of the reference run at every supported width, required identical | It proves "as before", not "as the cartridge": no emulator comparison exists |
| A heuristic for alternating sprites is fixed again with every report | No measurable target | A bench of 49 patterns first: the old code failed 27, the rewrite none | The bench holds patterns, not the reported scenes |
| With a display faster than announced the game runs 2.4 times too fast | "Paced by the display" with no floor | A pretend refresh rate in a test; fall back to the game's clock when presents return early | A real 60 Hz display was not used |
| On a slow device three of four pictures are skipped | After a skipped picture the next deadline lay in the future and the next frame counted as late again | Found only on a really slow target (an emulator), not with simulated slowness on the PC | No phone |
| Clicks in the sound when a frame is late | A frame's samples arrived with 2 to 7 ms to spare | A reserve held between 20 and 55 ms by a 0.4% speed trim: never empty in 7.5 minutes | Not listened to |
